# Trip Planner — глубокий разбор проекта по требованиям спецификации

Этот документ объясняет проект **с нуля, очень подробно и простыми словами** — так, чтобы понял даже человек, который видит его впервые (и даже школьник). Но при этом здесь **нет воды**: для каждого требования разобрано, **как именно** оно реализовано — какие алгоритмы, какие числа, какие промпты, что происходит, когда что-то ломается.

Структура каждого раздела одинаковая:
1. **Что просит спека** — точная формулировка требования.
2. **Что это значит простыми словами** — перевод на «человеческий» язык + аналогия.
3. **Как это сделано в проекте** — детально, с именами файлов и конкретными цифрами.
4. **Пример** — что реально происходит на живом запросе.
5. **Тонкости и защита от ошибок** — то, что отличает «студенческое демо» от «инженерного продукта».
6. **Где смотреть** — куда ткнуть пальцем на защите.
7. **Статус** — `ГОТОВО` / `ЧАСТИЧНО` / `НЕ ДЕЛАЛИ (осознанно)` с обоснованием.

## Часть 0. Что это за проект вообще (на пальцах)

**Trip Planner** — сайт, который **сам составляет план путешествия по дням**.

Представь: ты летишь в Стамбул на 4 дня, у тебя $500, ты любишь историю и ешь только халяль. Обычно пришлось бы часами искать музеи, проверять каждый ресторан на халяль, смотреть погоду, прикидывать маршрут и считать деньги. **Trip Planner делает это за 1–4 минуты.**

Ты:
1. Заполняешь форму (город, дни, бюджет, интересы, ограничения по еде); можешь приложить фото места.
2. Смотришь, как «робот-планировщик» собирает план по шагам (прогресс виден вживую).
3. Получаешь план по дням: реальные места со ссылками, рестораны с пометкой «халяль», погода, маршрут, итоговый бюджет.
4. Пишешь правки обычным текстом («убери музеи», «добавь халяльный ресторан») — робот точечно меняет план.
5. Жмёшь «принять» → скачиваешь PDF.

### Три «коробки», которые запускаются одной командой `docker compose up`

| Коробка | Что это | Простая аналогия |
|---|---|---|
| **Backend (мозг)** | Python, FastAPI + LangGraph, граф из 14 шагов | Дирижёр оркестра — решает, что делать в каком порядке |
| **3 MCP-сервера (руки)** | Отдельные программы-инструменты: карты, база знаний, калькулятор | Помощники, которым дирижёр раздаёт поручения |
| **Frontend (лицо)** | Сайт на React | То, что видит и трогает пользователь |

### Главные «умные слова» — сразу по-простому

- **LLM** (большая языковая модель, тут `gpt-4.1-mini`) — очень начитанный собеседник, который умеет писать текст, но сам по себе не ходит в интернет и не считает.
- **LangGraph** — блок-схема (flowchart) для робота: шаги, развилки, циклы.
- **MCP-сервер** — набор «рук» (инструментов), которыми LLM может что-то сделать в реальном мире.
- **RAG** — «учебник под рукой»: заранее собранные тексты, из которых в нужный момент достаём факты, чтобы модель не выдумывала.
- **Skill** — шпаргалка с правилами для LLM, чтобы результат всегда был в одном формате.
- **Evals** — экзамен для робота с автоматическими оценками.

Важно: это **учебный проект**. Цель — показать умение собрать «взрослый» AI-продукт из современных кирпичиков, а не запустить стартап.

## 3.1.1 — LangGraph workflow с ветвлениями, циклами и подтверждением человека

**Что просит спека:** оркестрация агентов через LangGraph; минимум один многошаговый workflow с условной логикой — **ветвления, циклы, человеческое подтверждение (HITL)**.

### Что это значит простыми словами

LangGraph — это **блок-схема для робота**. Вместо того чтобы делать всё в одну кучу, робот идёт по шагам, как по карте метро. Спека требует, чтобы на этой карте были:
- **Ветвления** — развилки «если…, то налево, иначе направо» (как в игре-бродилке «если есть ключ — открой дверь»).
- **Циклы** — возможность вернуться назад и пройти кусок заново (переделать план, если не понравился).
- **HITL (human-in-the-loop, «человек в цикле»)** — момент, когда робот **замирает и ждёт ответа человека**, прежде чем идти дальше.

Аналогия: представь повара-робота. Он не жарит всё сразу — он идёт по рецепту шаг за шагом. На развилке думает «есть ли у клиента аллергия?» (ветвление). Если блюдо не получилось — переделывает (цикл). А перед подачей **показывает тарелку клиенту и ждёт**: «нести или ещё поправить?» (HITL).

### Как это сделано в проекте

Граф состоит из **14 шагов (нод)**, собран в `backend/src/graph/builder.py` (функция `_build_state_graph`), развилки — в `backend/src/graph/branches.py`. Каждый шаг — отдельный файл в `backend/src/graph/nodes/`.

Полный маршрут робота (стрелки — это «рёбра» графа):

```
START
  │
  ▼
[1] collect_input ──── проверяет, что форма корректна (Pydantic-валидация)
  │
  ▼
{есть ли фото?}  ◄═══════════════ ВЕТВЛЕНИЕ 1 (has_photo)
  ├── да ──► [2] vision_identify ──► [3] enrich_input ──┐
  └── нет ───────────────────────────────────────────────┤
                                                          ▼
                                          [4] city_research  (RAG: изучить город)
                                                          │
                                                          ▼
                                          [5] candidate_places (найти места/еду/погоду)
                                                          │
                                                          ▼
                                          [6] budget_check (хватает ли денег?)
                                                          │
                              {бюджет реалистичен?}  ◄═══ ВЕТВЛЕНИЕ 2 (budget_feasible)
                              ├── НЕТ ──► [7] explain_and_ask (HITL — спросить человека)
                              │                 │
                              │                 └──► ЦИКЛ 1: назад в [4] city_research
                              │
                              └── ДА ──► [8] cluster_by_day (разбить места по дням)
                                              │
                                              ▼
                                         [9] optimize_route (построить маршрут внутри дня)
                                              │
                                              ▼
                                         [10] generate_plan (LLM пишет красивый план)
                                              │
                                              ▼
                                         [11] present_plan (HITL — показать человеку, ждать)
                                              │
                          {правка или принять?}  ◄═══════ ВЕТВЛЕНИЕ 3 (edit_or_accept)
                          ├── правка ──► [12] parse_edit_intent ──► [13] patch_plan
                          │                                              │
                          │                                              └─► ЦИКЛ 2: назад в [11]
                          └── принять ──► [14] finalize_and_export ──► END (→ PDF)
```

**3 ветвления** (`branches.py` — это маленькие функции, возвращающие имя следующего шага):
- `has_photo` — смотрит, есть ли `state.photo_b64` (загруженное фото). Есть → идём распознавать фото; нет → сразу к изучению города.
- `budget_feasible` — смотрит, выставлен ли `state.budget_warning`. Если предупреждения нет → план реалистичен, идём дальше; если есть → останавливаемся и спрашиваем человека.
- `edit_or_accept` — если человек нажал «принять» (`accept_signal`) → финализация; если прислал текст правки (`pending_edit_text`) → разбираем правку.

**2 цикла:**
- **Бюджетный цикл:** `explain_and_ask → city_research` (ребро в `builder.py`, строка 63). Если денег мало — робот объясняет ситуацию и **возвращается в начало сбора данных**, чтобы пересобрать более дешёвый вариант.
- **Цикл правок:** `patch_plan → present_plan` (строка 71). После каждой правки план снова показывается человеку — и так сколько угодно раз.

**2 точки подтверждения человека (HITL)** — реализованы через функцию LangGraph `interrupt()`:
- `explain_and_ask` — робот говорит «реалистичный минимум поездки $X, это выше бюджета — урезаю платные места» и ждёт решения.
- `present_plan` — робот показывает готовый план и ждёт: «правим или принимаем?».

`interrupt()` буквально **замораживает граф на середине**. Backend сохраняет всё состояние на диск, отдаёт паузу наружу, а когда человек ответит — граф **продолжается ровно с того же места** (через `Command(resume=...)`).

### Как робот «помнит» состояние между шагами

Всё состояние поездки лежит в одном объекте `TripState` (`backend/src/graph/state.py`) — это как **рюкзак, который робот несёт через все шаги**: туда складываются город, найденные места, рестораны, погода, готовый план, история правок. Каждый шаг достаёт из рюкзака нужное и кладёт обратно результат.

Это состояние **сохраняется на диск** после каждого шага (механизм `AsyncSqliteSaver`, файл `checkpoints/`). Поэтому даже если сервер перезапустить, работу можно продолжить с последней паузы. Технически тут есть тонкость (см. `builder.py`, функция `_checkpoint_serde`): чтобы при сохранении не терялись типы данных, проект явно перечисляет все свои модели — и собирает этот список автоматически из пакета `schemas`.

### Тонкости и защита от ошибок

- **Антизацикливание бюджета.** Если бы `budget_check` каждый раз заново ругался на бюджет, цикл `explain_and_ask → ... → budget_check → explain_and_ask` крутился бы вечно. Решение: после первого подтверждения ставится флаг `budget_acknowledged=True`, и `budget_check` на втором проходе сразу пропускает предупреждение (`budget_check.py`, строки 27–28).
- **Режим без человека для тестов.** Для автоматических evals человек физически не может нажимать кнопки. Поэтому `EVAL_MODE=true` заставляет `explain_and_ask` и `present_plan` **автоматически «соглашаться»** вместо `interrupt()` — иначе автотест завис бы навечно.

### Где смотреть
`backend/src/graph/builder.py` (сборка), `branches.py` (3 развилки), `backend/src/graph/nodes/` (14 файлов-шагов), `state.py` (рюкзак-состояние).

### Статус: ГОТОВО (с запасом)
Есть всё и по-настоящему: 14 шагов, 3 ветвления, 2 цикла, 2 реальные точки HITL, плюс сохранение состояния на диск. Это не «workflow для галочки», а сложный граф с обратными связями.

## 3.1.2 — Собственный MCP-сервер с 2–3 содержательными tool'ами

**Что просит спека:** минимум один свой MCP-сервер с 2–3 полезными инструментами.

### Что это значит простыми словами

LLM сама по себе умеет только **разговаривать**. Она не видит карту, не знает сегодняшнюю погоду, не умеет считать на калькуляторе. **MCP-сервер — это набор «рук», которые робот может попросить что-то сделать.** Каждая «рука» — это **tool** (инструмент): «найди музеи в Стамбуле», «дай погоду», «переведи доллары в лиры».

Аналогия: LLM — гениальный человек, запертый в комнате без окон и без интернета. MCP — это **телефон с кнопками**: нажал «погода» — тебе сказали погоду; нажал «карта» — тебе нашли музеи.

**Что такое MCP технически (просто):** это стандарт, по которому программа-«мозг» общается с программами-«инструментами». В этом проекте инструменты — это **не отдельные сайты**, а программы, которые backend **сам запускает как подпроцессы** (через так называемый stdio-транспорт) при первом обращении. За связь отвечает библиотека `langchain-mcp-adapters` (код подключения — `backend/src/mcp_clients/client.py`).

### Как это сделано в проекте

Требовался **1 сервер с 2–3 инструментами**. Сделано **3 сервера и 10 инструментов** — кратно больше.

#### Сервер №1 — `travel-tools` (связь с внешним миром, 4 инструмента)
Файл: `mcp_servers/travel-tools/server.py`. Никакой LLM-логики — только реальные бесплатные публичные API.

| Инструмент | Откуда данные | Что именно делает |
|---|---|---|
| `find_places` | OpenStreetMap (Overpass API) | Сначала находит координаты города (геокодинг Open-Meteo), потом ищет точки в радиусе **10 км** по категории. Категория → конкретный фильтр OSM: `museum→tourism=museum`, `park→leisure=park\|garden`, `religious→amenity=place_of_worship` и т.д. |
| `find_restaurants` | OpenStreetMap (теги `diet:*`) | Ищет рестораны в радиусе **8 км** с учётом dietary |
| `get_weather_forecast` | Open-Meteo | Прогноз по дням, до **16 дней** вперёд |
| `compute_route` | OSRM | Время и расстояние маршрута между точками |

**Как считается стоимость места (эвристика, `_make_place_from_element`):** если у объекта тег «вход бесплатный» или это парк/смотровая/религия — `$0`; если «вход платный» — средний тариф (`$15`); иначе — низкий (`$8`). Длительность визита тоже из таблицы: музей — 120 мин, парк — 60, смотровая — 30 и т.д.

**Как определяется халяль у ресторана (`_restaurant_from_element`):** если у объекта прямой тег `diet:halal=yes` — **уверенность 1.0** (подтверждено). Если прямого тега нет, но кухня из списка обычно-халяльных (турецкая, ближневосточная, ливанская, персидская, пакистанская…) — **уверенность 0.6** (вероятно). Рестораны с уверенностью ниже 0.5 в результат не попадают вовсе.

#### Сервер №2 — `city-knowledge` (доступ к собственной базе знаний / RAG, 3 инструмента)
Файл: `mcp_servers/city-knowledge/server.py`. Это «обёртка» вокруг векторной базы Qdrant.

| Инструмент | Что делает |
|---|---|
| `search_city_guide(city, query, k, section?)` | Превращает вопрос в вектор (эмбеддинг) и ищет в Qdrant **k** самых похожих по смыслу кусков путеводителя, с фильтром по городу (и опционально по разделу see/eat/...) |
| `get_city_overview(city)` | Возвращает сводку: валюта, языки, безопасность, транспорт, лучший сезон |
| `list_indexed_cities()` | Перечисляет, какие города вообще есть в базе (нужно для «вежливого» поведения, если города нет) |

#### Сервер №3 — `trip-utilities` (расчёты без интернета + 1 валютный API, 3 инструмента)
Файл: `mcp_servers/trip-utilities/server.py`.

| Инструмент | Что делает |
|---|---|
| `convert_currency` | Переводит валюты через frankfurter.app (курсы ЕЦБ); кэширует курс в памяти на **1 час**, чтобы не дёргать API лишний раз |
| `estimate_plan_cost` | Складывает стоимость плана: отдельно достопримечательности, рестораны, транспорт по дням, плюс проживание (`цена за ночь × (дни − 1)`) |
| `validate_dietary_match` | Чисто логическая проверка «подходит ли ресторан под ограничения» — без LLM. Возвращает вердикт: `accommodates` / `partial` / `does_not_accommodate` / `unknown` с объяснением |

### Пример (что происходит на запросе «Стамбул»)
Шаг графа `candidate_places` дёргает `travel-tools`: «найди historical, museum, viewpoint, park в Стамбуле» + «найди халяльные рестораны» + «дай погоду» — **всё одновременно**. Получает список реальных точек OSM с координатами, ценами, часами работы; список ресторанов с halal-маркерами; прогноз погоды.

### Тонкости и защита от ошибок (это уровень «инженерного продукта»)

- **Overpass постоянно падает (504).** Главный сервер OSM-поиска нестабилен. Поэтому `_overpass_query` делает **до 5 попыток через 3 разных зеркала** по кругу, с нарастающей паузой (1с, 2с, 4с, 8с) и жёстким таймаутом 15с на попытку. Деградировавшее зеркало «отваливается быстро», чтобы успеть к следующему.
- **Двухступенчатый поиск ресторанов.** Сначала ищем по строгому тегу `diet:halal=yes`. Если нашлось меньше 3 — добавляем мягкий поиск по типу кухни. Так план не остаётся без еды, даже если в OSM мало размеченных мест.
- **Единый формат ошибок.** Любой инструмент при сбое возвращает не «голое» исключение, а структурированный `ToolErrorResponse` с кодом (`TIMEOUT`, `NOT_FOUND`, `EXTERNAL_API_ERROR`) и флагом `retryable` (можно ли повторить). Шаги графа это понимают и спокойно пропускают сбойный кусок.
- **«Тонкий план лучше зависшего».** Шаг `candidate_places` ограничивает весь сбор данных **75 секундами** (`GATHER_BUDGET_SECONDS`). Если за это время медленный Overpass не ответил — его результат просто отбрасывается, а план собирается из того, что успело прийти. Лучше показать чуть более скромный план, чем вечно крутить «Генерация…».

### Где смотреть
Папка `mcp_servers/` (3 подпапки), документ `docs/MCP_SERVERS.md`, подключение — `backend/src/mcp_clients/client.py`.

### Статус: ГОТОВО (сильно сверх требования)
Нужен был 1 сервер с 2–3 tool'ами. Сделано 3 сервера с 10 tool'ами, с продуманной устойчивостью к сбоям внешних API.

## 3.1.3 — Собственный Skill с SKILL.md

**Что просит спека:** минимум один свой Skill, оформленный по стандарту — с файлом `SKILL.md`, описанием триггеров и валидной структурой.

### Что это значит простыми словами

Skill — это **готовая инструкция-памятка для LLM**, которую подключают к запросу. Это **жёсткая шпаргалка с правилами и образцом результата**. Без неё модель один раз напишет план так, другой раз — иначе. Со Skill — всегда одинаково и по правилам.

Аналогия: повар без рецепта каждый раз готовит по-своему. Skill — это **строгий рецепт с фотографией готового блюда**: «нарезать так, оформить вот так, проверить эти пункты перед подачей».

### Как это сделано в проекте

Skill называется **`itinerary-formatter`** (форматировщик плана). Файл — `skill/itinerary-formatter/SKILL.md`. Он оформлен по стандарту: вверху служебный блок (frontmatter) с полями `name`, `description` и списком **triggers** (когда применять), дальше — тело с правилами, структурой вывода и примером.

Его задача — **единый формат плана и для экрана, и для PDF**. Он подключается в **двух шагах** графа: `generate_plan` (первая генерация) и `finalize_and_export` (подготовка к PDF). Подгрузка — через `backend/src/llm/skill_loader.py`, текст Skill вставляется в системный промпт модели.

**5 жёстких правил из Skill (несоблюдение = провал):**
1. **Никогда не упоминать место, которого нет в данных** (`candidate_places` / `candidate_restaurants` / `city_context`). Если подходящего места нет — честно написать «не нашли вариант», а не выдумать.
2. **Каждое место — со ссылкой на источник** (OpenStreetMap или Wikivoyage) в формате `[название](ссылка)`.
3. **Не выдумывать цены и часы.** Только из инструментов; нет данных — писать «не указано».
4. **Соблюдать dietary буквально.** Ресторан без подтверждённого dietary-маркера (уверенность ≥ 0.5) в план не попадает.
5. **Не превышать дневной бюджет** или явно помечать превышение.

Также в Skill прописана **точная структура вывода** (шапка → дни с блоками Утро/День/Вечер → переходы между точками → сводная таблица бюджета → «что взять с собой» → источники), **правила dietary-маркеров** (зелёный кружок = подтверждено, жёлтый = вероятно) и **обработка краевых случаев** (город не в базе; бюджет недостижим; фото не загружено). В конце — **чек-лист самопроверки**, который агент проходит перед возвратом.

### Почему это важная вещь, а не формальность

Skill здесь — это **контракт между LLM и интерфейсом**. План рендерится в нескольких местах (первая генерация, перерисовка после правки, PDF) — и Skill гарантирует, что **везде он выглядит одинаково и не содержит выдумок**. Именно правило №1 («только реальные места») напрямую связано с метрикой `faithfulness` в evals (см. раздел 3.3).

### Где смотреть
`skill/itinerary-formatter/SKILL.md`; подключение — `backend/src/llm/skill_loader.py`, использование — в нодах `generate_plan.py` и `finalize_and_export.py`, а также при перерисовке в `patch_plan.py`.

### Статус: ГОТОВО
Skill есть, оформлен по стандарту (frontmatter + триггеры + структура), реально применяется в трёх местах рендеринга и несёт смысловую нагрузку (защита от галлюцинаций).

## 3.2.1 — RAG-пайплайн с осознанным выбором компонентов

**Что просит спека:** RAG с продуманным выбором: стратегия нарезки (chunking), модель эмбеддингов, векторная БД (Qdrant), reranker (по желанию).

### Что это значит простыми словами

RAG (Retrieval-Augmented Generation) — это способ дать LLM **«учебник под рукой»**, чтобы она не выдумывала факты. Заранее собираем тексты (путеводители по городам), режем на кусочки, складываем в специальную базу. В момент запроса **достаём только нужные кусочки** и подсовываем модели: «вот факты, опирайся на них».

Аналогия: на экзамене вместо «вспоминай сам» тебе разрешили принести **конспект**. Перед каждым вопросом находишь нужный абзац и отвечаешь по нему.

**Что такое «эмбеддинг» и «векторная база» (просто):** компьютер не понимает слова, но умеет считать. Эмбеддинг — это превращение куска текста в **список из 1536 чисел**, которые кодируют его смысл. Похожие по смыслу тексты получают похожие числа. Векторная база (Qdrant) хранит эти числа и умеет быстро находить «самые близкие по смыслу» — поэтому поиск идёт **по смыслу, а не по точному совпадению слов** («где поесть» найдёт абзац про рестораны, даже если слова «поесть» там нет).

### Как это сделано в проекте — по шагам

```
Страница города на Wikivoyage (бесплатный вики-путеводитель)
        │  (скачивание через API — см. требование 3.2.2)
        ▼
НАРЕЗКА по смысловым секциям: See / Do / Eat / Drink / Sleep / Get around
   (backend/src/rag/chunking.py)
        │
        ▼
ЭМБЕДДИНГ каждого куска моделью OpenAI text-embedding-3-small → 1536 чисел
   (backend/src/rag/embeddings.py)
        │
        ▼
СКЛАДЫВАНИЕ в Qdrant — ОДНА общая коллекция "trip_planner_v1" на ВСЕ города,
   у каждого куска метки: { city, section, kind, source_url, ingested_at }
   (backend/src/rag/qdrant_client.py)
        │
        ▼
ПОИСК через MCP: city-knowledge.search_city_guide(city, query, section?)
```

### Осознанность выбора (а это спека ценит выше всего)

- **Нарезка по секциям, а не «каждые N символов».** Wikivoyage устроен по стабильным разделам (See/Do/Eat/Drink/Sleep/Get around). Код (`chunking.py`) разбивает текст по заголовкам вида `== See ==`, приводит названия к стандартным ключам (`SECTION_MAP`: «Buy»→do, «Get in»→get-around и т.д.), а слишком длинные секции (> **2400 символов**) дополнительно режет по абзацам, не разрывая мысль. Очень короткие куски (< **200 символов**) отсекаются. **Почему так:** кусок, ограниченный одной темой («где поесть»), даёт более точный поиск и меньше «шума», чем механическая нарезка по длине.
- **Модель эмбеддингов `text-embedding-3-small` (1536 измерений)** — дешёвая, быстрая, от того же поставщика (OpenAI), что и основная модель. Для путеводителей её точности достаточно.
- **Одна коллекция на все города + фильтр по полю `city`**, а НЕ отдельная коллекция на каждый город. Это сознательное решение: проще управлять одной коллекцией, а фильтр по метаданным в Qdrant работает быстро. Поиск всегда идёт с фильтром `city=... AND kind=guide` (см. `search_city_guide` в `city-knowledge/server.py`).
- **Технический нюанс совместимости:** клиент Qdrant специально «запинен» (зафиксирован) на версию 1.11.x под версию сервера, и весь код использует современный метод `query_points(...)` (а не устаревший `.search()`). Это убирает предупреждения о несовместимости — мелочь, но показывает аккуратность.
- **Reranker** (дополнительное переупорядочивание результатов «вторым проходом») спекой помечен как **необязательный**. В проекте его нет — оставлен как идея на будущее (stretch goal).

### Что лежит в базе на самом деле
Для каждого города хранятся два типа записей (поле `kind`): **`guide`** — куски путеводителя для поиска по смыслу, и **`overview`** — одна запись со сводкой города (валюта, языки, безопасность, транспорт, сезон) в виде JSON. Поиск `search_city_guide` берёт `guide`, а `get_city_overview` — `overview`.

### Проиндексировано 5 городов
Istanbul, Barcelona, Lisbon, Tokyo, Mexico City.

### Где смотреть
`backend/src/rag/` (chunking.py, embeddings.py, qdrant_client.py), скрипт наполнения `scripts/ingest_wikivoyage.py`, MCP-сервер `mcp_servers/city-knowledge/server.py`.

### Статус: ГОТОВО
Все обязательные компоненты RAG есть, выбор каждого обоснован (стратегия нарезки, модель эмбеддингов, одна коллекция + фильтр). Reranker (необязательный) сознательно не делали.

## 3.2.2 — Обработка документов или скрапинг сайтов

**Что просит спека:** парсинг PDF/DOCX/HTML или скрапинг сайтов (в т.ч. с динамическим контентом).

### Что это значит простыми словами

«Скрапинг» — это когда программа **сама заходит на сайт, скачивает страницу и вытаскивает оттуда нужный текст**, как будто человек скопировал текст вручную, только автоматически. Спека хочет, чтобы данные приходили из реального источника, а не были вписаны руками.

### Как это сделано в проекте

Скрипт `scripts/ingest_wikivoyage.py` скачивает страницы городов с **Wikivoyage** и готовит их для RAG-базы (это и есть «топливо» для требования 3.2.1). По шагам:

1. **Скачивание.** Используется официальный API Wikivoyage (`action=parse`), который отдаёт исходный «вики-текст» страницы — это надёжнее, чем парсить готовый HTML.
2. **Очистка (`_wikitext_to_plain`).** Вики-текст полон служебной разметки. Серия регулярных выражений выкидывает шаблоны `{{...}}` (в т.ч. вложенные), ссылки на файлы/картинки, сноски, HTML-теги, а из ссылок `[[Страница|подпись]]` оставляет только читаемую подпись. На выходе — чистый текст с сохранёнными заголовками секций.
3. **Нарезка** тем же модулем `chunking.py` (см. выше).
4. **Эмбеддинг** каждого куска (`text-embedding-3-small`).
5. **Загрузка в Qdrant** с метками. У каждого куска уникальный id (MD5-хэш от города+секции+текста — чтобы повторный запуск не плодил дубликаты).

Плюс на каждый город сохраняется запись-сводка `overview` из встроенной таблицы `CITY_META_DEFAULTS` (валюта, языки, безопасность, транспорт, сезон) — это курируемые данные, дополняющие скрапинг.

### Тонкости
- Между городами пауза 1.5с — вежливость к серверу Wikivoyage.
- Есть режим `--dry-run` (прогон без записи и без трат на эмбеддинги) — для проверки нарезки.
- Скрипт сам определяет, где он запущен (в Docker или локально), и подстраивает пути.

### Где смотреть
`scripts/ingest_wikivoyage.py`, `backend/src/rag/chunking.py`.

### Статус: ГОТОВО
Реальный скрапинг внешнего сайта (Wikivoyage) с нетривиальной очисткой вики-разметки для 5 городов.

## 3.2.3 — Мультимодальность (vision / OCR / audio / видео)

**Что просит спека:** хотя бы одна мультимодальная возможность, использованная **осмысленно**, а не «для галочки».

### Что это значит простыми словами

Обычно модель работает с **текстом**. «Мультимодальность» — это когда она работает ещё и с **картинками, звуком или видео**. Спека требует добавить хотя бы одно — и чтобы это было **по делу**, а не «распознали и забыли».

### Как это сделано в проекте — анализ изображений (vision)

Пользователь может **загрузить фото места** (например, скриншот из инстаграма с красивым зданием) и спросить «что это и стоит ли ехать?». Цепочка:

1. **Загрузка.** Фронт (`PhotoUpload.tsx`) отправляет фото на backend (`POST /sessions/{id}/photo`, до 5 МБ), оно превращается в base64-строку и кладётся в состояние (`photo_b64`).
2. **Распознавание (шаг `vision_identify`).** Если фото есть, граф уходит на эту ветку. Фото отправляется в **`gpt-4.1-mini` в режиме vision** — это **та же модель**, что пишет план (отдельную не заводили). Температура низкая (0.1 — нужен факт, не фантазия).
3. **Результат.** Модель возвращает JSON, который превращается в `PhotoAnalysis { landmark, city, place_type, description, confidence }`. Например: `{ "Blue Mosque", "Istanbul", "religious", уверенность 0.95 }`. Код аккуратно снимает обёртку ` ```json ` , если модель её добавила, и при ошибке парсинга просто продолжает без фото (не падает).
4. **Вплетение в план (шаг `enrich_input`).** Здесь видно, что это **не для галочки**:
   - тип места с фото (например, `religious`) **добавляется в интересы** пользователя — значит, план учтёт это при подборе мест;
   - если пользователь **не указал город**, а уверенность распознавания **≥ 0.7** — город берётся прямо с фото;
   - данные фото уходят дальше в `generate_plan`, и при уверенности ≥ 0.6 это место включается в план.

### Пример
Загрузил фото Голубой мечети, город не указал → модель определяет «Blue Mosque, Istanbul, religious, 0.95» → город автоматически становится Istanbul, в интересы добавляется `religious`, а сама мечеть попадает в план.

### Где смотреть
`backend/src/graph/nodes/vision_identify.py`, `enrich_input.py`, `backend/src/api/photo.py`, `backend/src/llm/client.py` (функция `ainvoke_text` с параметром `images`), фронт `frontend/src/components/PhotoUpload.tsx`.

### Статус: ГОТОВО
Vision встроен по-настоящему: результат влияет на интересы, может задать город и попасть в итоговый план. Это «осмысленное» использование, как требует спека.

## 3.3.1 — Логирование и трейсинг всех LLM-вызовов через LangSmith

**Что просит спека:** все обращения к LLM логируются и трассируются через LangSmith; на защите показать дашборд с реальными трейсами.

### Что это значит простыми словами

Когда робот общается с моделью, важно **видеть, что именно он спросил и что получил** — для отладки и понимания. LangSmith — это как **«чёрный ящик» самолёта**: он автоматически записывает каждый запрос к LLM, ответ, сколько времени заняло и сколько стоило. Потом всё это видно на сайте-дашборде в виде дерева вызовов.

### Как это сделано в проекте

- **Включается одной переменной окружения** `LANGSMITH_TRACING=true`. После этого LangSmith записывает **всё автоматически** — менять код графа не нужно.
- **Полнота покрытия гарантирована архитектурой:** все обращения к LLM идут через **один-единственный файл** `backend/src/llm/client.py` (функции `ainvoke_text` и `ainvoke_structured`). Ноды не создают модель напрямую. Раз всё течёт через одну «трубу», то и трассируется всё.
- **Есть реальные сохранённые прогоны** (их можно открыть на защите): проекты `mini-41-8980574a` и `mini-4o-ebf8458a` (два прогона A/B-теста) и датасет `trip-planner-golden-v1`.

### Где смотреть
Настройка — `backend/src/config.py` и `main.py` (lifespan логирует, включён ли трейсинг); единая «труба» — `backend/src/llm/client.py`. На защите — открыть дашборд LangSmith по именам проектов выше.

### Статус: ГОТОВО
Автотрейсинг включён, покрытие полное (single-client архитектура), есть реальные проекты для демонстрации.

## 3.3.2 — Evals: golden dataset, автопрогон, минимум 2 метрики

**Что просит спека (раздел 3.3):** golden dataset **не менее 30 примеров**, автоматический прогон, минимум 2 метрики.
**Что просит чек-лист (раздел 8):** golden dataset **10+ примеров** и автоматизированные evals.

### Что это значит простыми словами

«Evals» — это **экзамен для робота**. Заранее придумываем набор задач с известными свойствами (это golden dataset, «золотой набор»), прогоняем на них робота и **автоматически ставим оценки** по нескольким критериям. Так качество измеряется числами, а не «на глаз».

«LLM-as-judge» — это когда **другая модель работает учителем-проверяющим**: читает план и ставит оценку по заданному критерию. Аналогия: одна модель «написала сочинение», вторая — «проверяет его по чёткому списку критериев».

### Как это сделано в проекте

- **Golden dataset — 10 примеров** (`evals/dataset.jsonl`, в LangSmith под именем `trip-planner-golden-v1`). Покрытие продумано: 5 проиндексированных городов + 1 непроиндексированный (Париж — проверка «а что если данных нет?»), 2 кейса с фото, 4 разных dietary (halal, vegan, vegetarian, gluten-free), 3 «трудных» кейса (мало денег, противоречивые интересы, город без индекса).

- **2 метрики, обе — LLM-as-judge** (проверяющий — `gpt-4.1-mini`, температура **0.0** для воспроизводимости):

  **1) `constraint_adherence` (соблюдение ограничений)** — `evals/judges/constraint_adherence.py`. Судья проверяет три вещи и ставит общий «прошёл/не прошёл»:
  - Бюджет: общая стоимость не выше заявленной (и если в плане прямо написано «превышение на $X» — это уже провал).
  - Dietary: у каждого ресторана есть подходящий маркер (мягкий жёлтый маркер засчитывается, отсутствие маркера — провал).
  - Дни: в плане ровно столько дней, сколько просили (считает заголовки `## День N`).
  - Оценка: 1.0, если прошли все три, иначе 0.0. Цель ≥ 0.80.

  **2) `faithfulness` (честность / отсутствие выдумок)** — `evals/judges/faithfulness.py`. Судья:
  - выписывает все названия мест из плана;
  - собирает все названия, реально пришедшие из инструментов (они хранятся в `tool_calls_aggregated` — каждый шаг графа складывает туда «что вызвал и что получил»);
  - сверяет одно с другим (без учёта регистра, допуская мелкие различия в написании и переводы);
  - всё, чего нет в данных инструментов, считает **галлюцинацией (выдумкой)**.
  - Оценка = доля «честных» мест. Цель ≥ 0.95.

- **Автопрогон** — `evals/run.py`. Скрипт принудительно включает `EVAL_MODE=true` **до** импорта графа (важен порядок — настройки кэшируются), создаёт «свежий» граф без сохранения на диск, прогоняет каждый пример датасета и отдаёт результаты в LangSmith через `langsmith.evaluate`. Результаты выгружаются в CSV.

### Пример работы судьи `faithfulness`
План написал «ужин в ресторане Pierre Gourmet». Судья ищет «Pierre Gourmet» среди названий, что вернул `find_restaurants`. Не нашёл → это выдумка → балл снижается. Именно так поймали разницу между моделями в A/B (см. ниже).

### ЧЕСТНОЕ ПРЕДУПРЕЖДЕНИЕ (важно для защиты)

В самой спеке есть **внутреннее противоречие**: раздел 3.3 требует «не менее 30 примеров», а чек-лист (раздел 8) — «10+». **В проекте сделано 10** — это соответствует чек-листу, но **не дотягивает до строгой цифры 30** из раздела 3.3. Выбор осознанный и задокументирован в `docs/PROJECT_SPEC.md` (каждый прогон стоит денег — вызовы платной модели × 2 метрики × 2 варианта модели).

**Это главный формальный риск проекта.** На защите стоит проговорить это самому: «датасет 10, покрытие осмысленное, при необходимости легко расширяется до 30». Механика evals полностью рабочая — добавить примеры в `dataset.jsonl` и перезапустить.

### Тонкости
- **Судьи асинхронные, а `langsmith.evaluate` запускает их в обычных потоках без «событийного цикла».** Поэтому в `evals/judges/__init__.py` есть синхронные обёртки, которые внутри вызывают `asyncio.run(...)`. Иначе был бы краш «no current event loop».
- **LangGraph возвращает «смешанный» результат** (верх — словарь, но вложенные объекты остаются pydantic-моделями). Поэтому `run.py` аккуратно приводит их через `model_dump()`, а не надеется на автоматику.

### Где смотреть
`evals/dataset.jsonl`, `evals/run.py`, `evals/judges/` (обе метрики + обёртки), результаты `evals/results/mini-41.csv` и `mini-4o.csv`, план — `docs/EVALS_PLAN.md`.

### Статус: ЧАСТИЧНО (по букве 3.3) / ГОТОВО (по чек-листу п.8)
Механика evals полностью рабочая: 2 содержательные метрики, автопрогон, осмысленное покрытие. Не хватает только объёма датасета до строгих «30».

## 3.3.3 — A/B тестирование

**Что просит спека:** хотя бы один эксперимент со сравнением двух конфигураций (модели/промпты/температуры/RAG) с метриками и выводами.

### Что это значит простыми словами

A/B-тест — это **честное соревнование двух вариантов на одинаковых задачах**. Меняем **только одну вещь** (здесь — модель), всё остальное держим идентичным, и смотрим по числам, кто лучше. Так решения принимают «на данных», а не «мне кажется».

### Как это сделано в проекте

Сравнили **две модели** на одном и том же golden dataset: `gpt-4.1-mini` (основная) против `gpt-4o-mini` (вторая). Менялась **только модель** (через переменные окружения `OPENAI_MODEL` / `OPENAI_MODEL_B`) — RAG, промпты, инструменты, эмбеддинги, температуры были одинаковыми.

Результат (`evals/results/ab_mini_41_vs_4o.md`):

| Метрика | gpt-4.1-mini | gpt-4o-mini | Разница |
|---|---:|---:|---:|
| `constraint_adherence` | 0.800 | 0.800 | 0.000 (ничья) |
| `faithfulness` | **0.965** | 0.507 | **−0.458** (огромный разрыв) |

### Вывод (простыми словами)
По соблюдению ограничений модели равны. Но по «честности» `gpt-4o-mini` **выдумывает примерно половину названий мест** (0.507 — это чуть лучше подбрасывания монетки). А у проекта жёсткое правило из Skill: «только реальные места из данных». Поэтому `gpt-4o-mini` для основной работы **не годится**, и выбор `gpt-4.1-mini` — **не вкусовщина, а вывод из чисел**.

Это идеальный учебный результат: A/B-тест не просто «прогнали для галочки», а **реально повлиял на ключевое решение** (какую модель ставить основной).

### Тонкость
В отчёте честно отмечено: на датасете из 10 примеров разница меньше 0.05 — это «в пределах шума». Поэтому ничья по `constraint_adherence` (0.000) — действительно ничья, а вот разрыв в 0.458 по `faithfulness` — настоящий, ему можно верить.

### Где смотреть
`evals/results/ab_mini_41_vs_4o.md` + две CSV-таблицы рядом; скрипт сравнения `evals/compare_experiments.py`.

### Статус: ГОТОВО
Настоящий A/B с идентичными условиями, чёткими метриками и выводом, который повлиял на архитектурное решение.

## 3.4.1 — Обоснованный выбор LLM

**Что просит спека:** документированный выбор модели (GPT/Claude/Gemini/локальная) с явным балансом стоимости, латентности и качества.

### Что это значит простыми словами

Моделей много, и они разные: одни умнее, но дороже и медленнее; другие дешевле и быстрее. Спека требует **не брать модель наугад, а объяснить выбор** — с учётом цены, скорости и качества.

### Как это сделано в проекте

Выбрана **семья OpenAI mini**, основная модель — **`gpt-4.1-mini`**. Подход «одна модель на всё»: она используется в **каждом** месте, где нужен интеллект — генерация плана, vision (фото), разбор правок, оба судьи в evals, финализация. Это сознательно проще и дешевле, чем держать «умную для сложного, дешёвую для простого».

Обоснование (из `docs/PROJECT_SPEC.md`):

| Критерий | Почему `gpt-4.1-mini` подходит |
|---|---|
| **Стоимость** | дешёвая mini-модель (~$0.40 за млн входных, ~$1.60 за млн выходных токенов) → весь проект дешёвый; evals × 2 модели ≈ $0.5–2 |
| **Структурный вывод / tool-use** | стабильный strict-режим — разбор правок (`with_structured_output`) работает без «танцев с бубном» вокруг парсинга |
| **Vision** | встроен в ту же модель → не нужна отдельная модель для фото, одна нода `vision_identify` |
| **Интеграция** | `langchain-openai` — самый зрелый коннектор в экосистеме, меньше возни |
| **Длинный контекст** | до 1 млн токенов — большой запас на случай, если придётся «впихнуть» весь контекст |
| **Качество (по evals)** | faithfulness 0.965 против 0.507 у конкурента — выбор подтверждён цифрами |

**Кого не выбрали и почему:** Anthropic Claude — запрещён условием задачи; Google Gemini — изначально планировали, но заказчик попросил OpenAI; Qwen — менее зрелая интеграция, vision отдельной моделью (лишний шаг).

### Где смотреть
`docs/PROJECT_SPEC.md`, раздел «LLM choice rationale»; подтверждение — A/B-результаты (`evals/results/ab_mini_41_vs_4o.md`).

### Статус: ГОТОВО
Выбор задокументирован по всем критериям спеки (цена/качество/интеграция) и, что особенно ценно, **подкреплён экспериментальными цифрами**, а не только словами.

## 3.4.2 — Подбор температуры, top_p, max_tokens с обоснованием

**Что просит спека:** настройку `temperature`, `top_p`, `max_tokens` с экспериментальным обоснованием.

### Что это значит простыми словами

Это «крутилки» поведения модели:
- **temperature (температура)** — насколько модель «фантазирует». 0 = строго и предсказуемо, 1 = креативно и разнообразно.
- **top_p** — похожая крутилка разнообразия (из какого «облака» вероятных слов выбирать).
- **max_tokens** — максимальная длина ответа (чтобы план не обрывался, а короткая правка не раздувалась).

Главная идея: для **творческого** текста (описания мест) — температура повыше; для **строгого** (разобрать правку в структуру, поставить оценку) — поближе к нулю.

### Как это сделано в проекте

| Где | temperature | max_tokens | Почему именно так |
|---|---|---|---|
| Генерация плана (`generate_plan`) | **0.7** | 4096 | нужны живые, разнообразные описания мест; факты всё равно берутся из RAG/инструментов, так что «фантазия» не врёт |
| Разбор правки (`parse_edit_intent`) | **0.1** | 512 | нужен чёткий, стабильный структурный результат без разброса; правка — короткая |
| Распознавание фото (`vision_identify`) | **0.1** | 512 | нужен факт «что это за место», а не сочинение |
| Перерисовка плана после правки (`patch_plan`) | **0.4** | 4096 | компромисс: чуть живее, но осторожнее, чем первая генерация |
| Судьи в evals | **0.0** | 600–800 | оценка должна быть воспроизводимой (одинаковой при повторе) |
| top_p | **0.95** (по умолчанию) | — | оставлен дефолтным осознанно — не было причин трогать обе крутилки разнообразия сразу |

Значения заданы в едином клиенте `backend/src/llm/client.py` (дефолты `temperature=0.7`, `max_tokens=4096`) и переопределяются в каждой ноде под её задачу.

### Честное замечание для защиты
Обоснование здесь скорее **инженерно-логическое** («творчество vs строгость»), чем «прогнали 10 значений температуры и построили графики». В `docs/PROJECT_SPEC.md` прямо написано: значения стартовые, проверены на примерах из golden dataset. Если ментор спросит про **эксперименты** с температурой — стоит честно сказать, что отдельного A/B по температуре не делали (делали A/B по модели), а значения подобраны по принципу «факт = низкая, креатив = высокая».

### Где смотреть
`docs/PROJECT_SPEC.md` (раздел «Hyperparameters»), реальные значения — `backend/src/llm/client.py` и аргументы в нодах графа.

### Статус: ГОТОВО (с нюансом)
Все три параметра настроены под конкретные задачи и обоснованы логически. Единственный нюанс — обоснование не «экспериментальное в строгом смысле» (нет A/B по температурам).

## 4. Рекомендуемые требования (не обязательны, но повышают оценку)

Эти пункты **не нужны для допуска**, но за них дают баллы. Здесь честно: что сделано, а что осознанно пропущено (многое прямо помечено в `docs/PROJECT_SPEC.md` как «вне scope v1» — то есть не забыто, а сознательно отложено).

### 1. Guardrails (защитные «перила») — ЧАСТИЧНО
**Что это:** фильтры на входе и выходе — защита от взлома промпта (prompt injection), от утечки личных данных (PII), от токсичности.
**В проекте:** есть **доменный guardrail на выходе** — жёсткие правила Skill, запрещающие выдумывать места/цены (и метрика `faithfulness` это измеряет). Но **нет** отдельного фильтра персональных данных и **нет** специальной защиты от prompt injection. Поэтому — частично.

### 2. Кэширование (semantic / prompt cache) — НЕ ДЕЛАЛИ (осознанно)
**Что это:** запоминать ответы, чтобы не платить дважды за одно и то же.
**В проекте:** прямо помечено «вне scope v1». Маленькое исключение — кэш курсов валют на 1 час в `trip-utilities`, но это не про LLM.

### 3. Fallback между моделями — НЕ ДЕЛАЛИ
**Что это:** если основная модель упала или слишком дорогая — переключиться на запасную.
**В проекте:** есть **повторные попытки** при сбое (retry с нарастающей паузой в `llm/client.py`), но **переключения на другую модель нет**. Помечено как идея на будущее (mini → полная модель). Важно не путать: retry ≠ fallback.

### 4. Docker + docker-compose — ГОТОВО
**Что это:** упаковать проект так, чтобы запускался одной командой.
**В проекте:** `docker compose up` поднимает весь стек (qdrant + backend + frontend); MCP-серверы backend запускает сам как подпроцессы.

### 5. CI/CD (GitHub Actions с автозапуском evals на PR) — НЕ ДЕЛАЛИ (осознанно)
**Что это:** автоматическая проверка кода при каждом изменении.
**В проекте:** прямо «вне scope v1».

### 6. Деплой на публичный URL (Render) — НЕ ДЕЛАЛИ
**Что это:** выложить сайт в интернет по ссылке.
**В проекте:** вместо этого — запуск локально одной командой (спека это разрешает как замену деплою, см. артефакты). Render помечен как опциональный stretch-goal.

### 7. Аутентификация и роли — НЕ ДЕЛАЛИ (осознанно)
**Что это:** логин/пароль, права пользователей.
**В проекте:** сессии анонимные по UUID; auth «вне scope v1».

### 8. Голосовой интерфейс — НЕ ДЕЛАЛИ (осознанно)
**Что это:** управление голосом (audio-to-audio).
**В проекте:** «вне scope v1».

### 9. Интеграция с реальными внешними API — ГОТОВО
**Что это:** подключение к настоящим сервисам.
**В проекте:** проект ходит в реальные публичные API: OpenStreetMap/Overpass (места), Open-Meteo (погода), OSRM (маршруты), frankfurter.app (валюты). Это полноценная интеграция, а не моки.

### Итог по рекомендуемым
Уверенно сделаны **Docker (4)** и **внешние API (9)**, частично — **Guardrails (1)**. Остальное осознанно отложено и **задокументировано** как «вне scope» — а умение явно очертить границы продукта спека ценит (раздел 1: «осознанный выбор каждого технического решения»).
